# Decisions

Settled decisions and what they replaced. Agents: do not reopen a settled decision; propose an RFC instead.

| # | Decision | Status | Replaces / notes |
| --- | --- | --- | --- |
| D1 | Two repos: `engine` (original work) and `components` (reference set) | Settled | Single repo with a components package |
| D2 | Engine packages: `core`, `runtime`, `renderer`, `editor`, `theme` (+ `testing/`, `fixtures/`) | Settled | Earlier 4-package plan without `runtime`. Added because every mature comparable project separates headless state/logic from the view layer. |
| D3 | Dependency direction: everything points toward `core`; registry and data adapter are injected by the host | Settled | — |
| D4 | Runtime is the primary mode; build-time is bundled JSON in the same slot | Settled | — |
| D5 | Two inputs (documents, records), two writers (editor writes documents, pages write records) | Settled | Form.io two-document model |
| D6 | Documents split into `entity` (fields, validation) and `view` (`form`, `table`, `dashboard`) | Settled | Earlier single `{page, fields}` schema |
| D7 | `specVersion` (engine format, needs migrations) is separate from `revision` (user edits, data) | Settled | Earlier rule "every schema change bumps version and ships a migration" |
| D8 | Conditions are a JSON AST; no string expressions | Settled | amis-style expressions rejected |
| D9 | Exact-key registry with `Input`, `Display`, optional `CellEditor`, plus `FieldFrame` template | Settled | Ranked testers (JSON Forms) rejected |
| D10 | Own styled components and logic; accept Radix/React Aria and TanStack in the components repo. The editor's dashboard drag/resize is hand-written over CSS grid (pointer drag + arrow keys), not react-grid-layout | Settled | Earlier "own everything, import nothing" stance; the planned react-grid-layout v2 + `@dnd-kit/react` editor deps were dropped when the layout editor landed (`1d3f81c`, 2026-10-04): react-grid-layout is not keyboard accessible, and the hand-written version is a few hundred lines behind no adapter |
| D11 | Do not fork or build on Object UI; read it as reference only | Settled | Churn (v0→v17 in ~6 months), ObjectStack coupling, ~133 weekly downloads |
| D12 | Real apps are exit criteria: intake form (Phase 2), to-do (Phase 3), Fitnotes clone (Phases 4–5) | Settled | Feature-checklist phases |
| D13 | The contract is in flux (`specVersion` has moved with each format change; the current value is in `ARCHITECTURE.md` §8); no `contract-vN` freeze or tag is planned, so the engine and components repos both move as versions are published | Settled | Replaces "freeze `contract-v0` before parallel agent work." `specVersion` still bumps with `migrate()` steps when the format actually changes (AGENTS.md rule 8); a future freeze is a separate decision, not a deadline |
| D14 | Agents land and release their own work: solo mode commits straight to `main`, parallel agents work in worktrees under `.worktrees/` with one writer at a time per branch | Settled | Replaces "2–4 concurrent agents, one package per PR, CODEOWNERS on `core`" (`a98e758`, 2026-10-10): the review gates left finished work unreleased, blocking every agent that depended on it |
| D15 | Components are styled through a public, host-configurable CSS surface: theme tokens (`--yadad-*`), per-component CSS variables that default to tokens, stable `data-part` hooks, and all CSS in `@layer yadad` so host styles win. Authored in plain CSS and shipped as pre-built CSS that hosts may import or skip. | Settled | Open question "Tailwind or plain CSS variables"; chosen for maximum host configurability with no build-tool lock-in |
| D16 | Test-only dev dependencies (DOM environments, testing libraries, axe) may be added without an RFC | Settled | AGENTS.md rule 7 now covers runtime and published dependencies only |
| D17 | Packages publish to the GitLab npm registry (`gitlab.base-camp.dev`), with GitHub as the source repo; GitLab CI publishes any `@yadad/*` version the registry lacks | Settled | The publish job uses only the GitLab job token (no npm token), `origin` pushes to both remotes, and versions come from `pnpm changeset version`, so the mirror can never diverge (`.gitlab-ci.yml`, `tools/release/publish.sh`, since `23bd519`, 2026-10-06) |
| D18 | Dashboard grid rows have a fixed height: `gridAutoRows: var(--yadad-grid-row-height, 4rem)` in both the renderer and the editor | Settled | `h` then means "N rows" in both modes, so an edit in the editor looks like its render (`e69a7be`, 2026-10-04; stacked mobile mode is the documented exception, rows go `auto`) |
| D19 | The theme package owns token names: `TOKEN_NAMES` in `@yadad/theme` is the list, each becoming `--yadad-<name>` | Settled | Resolves the open question in ARCHITECTURE.md §3 ("where they live, core or theme"); names freeze with the contract, values stay free (`9c81486`, 2026-10-04) |
| D20 | Test files in every package may import `@yadad/testing` (the mock registry); production files may not | Settled | The mock registry keeps renderer/editor tests component-free; enforced by dependency-cruiser (`a585c84`, 2026-10-04, the `-in-tests` rules) |
| D21 | One slim showcase (`apps/showcase`) is the only example app in the repo; `examples/` is reserved and stays empty | Settled | The showcase renders the fixtures and exercises every package; more example apps would multiply the surface a general-purpose library must be tested against (showcase since `ae679de`, 2026-10-04; `examples/.gitkeep` only) |
| D22 | Conditions get a structured relative date, `{ "daysFromToday": N }` (0 today, -7 a week ago), as the value of eq/neq/gt/gte/lt/lte on `date` fields only. The runtime resolves it to a local "YYYY-MM-DD" before evaluating a condition and before any `DataAdapter` call, so adapters, servers and the records protocol only see fixed dates. specVersion is 1; version 0 documents stay valid and `migrate()` stamps them | Settled | Hard-coded dates in "today's sets" views, and string expressions (D8). A single integer was chosen over units or keywords ("today", "startOfWeek"): it is enough for rolling windows and cannot be mis-parsed. `in` and `contains` reject it. Number and date quick filters are a from/to range (gte/lte) with no document change: a field id in `quickFilters` already means "filter by this field" |
| D23 | `testing` imports `core` and `runtime` and never `renderer` or `editor`; `checkViewStates` takes the host's `render` function. Its three entry points are the index, `contract-kit` and `state-checks` | Settled | The renderer's and editor's tests import `testing`, so importing them back would be a cycle. `state-checks` and `contract-kit` need Vitest and a DOM, so they are separate entries and the index stays free of them. Enforced by dependency-cruiser (`testing-imports-core-runtime-only`) |
| D24 | The state grid is derived from documents: `viewStates(view, documents, { now })` is a pure function whose axes are plain data. The caller always passes `now` | Settled | Hand-written state lists drift from the documents they cover. `now` is required so the same input always gives the same states; new axes are added by extending `StateAxisKind` and combining with `combineAxes`, not by special cases |
| D25 | The grid lists every combination of axes when it fits in `limit` (default 24), otherwise a deterministic pairwise cover (every pair of values from two axes appears in at least one state); embedded views of a dashboard get a smaller limit (3). `complete` says whether even the cover fit | Settled | A full product grows too fast (a form with conditions, a viewer and records is thousands of states); defects are mostly caused by one or two axes together. A random sample would make failures unrepeatable |
| D26 | Source states (loading, error, refused, conflict) are added by `testing`, one extra state per applicable source, not crossed with every data state | Settled | Crossing multiplies states for little coverage. Loading and error show no data, so they use the first state; refused and conflict use the fullest state, since they need something to write. Where a source applies depends on the view (a read-only table cannot be refused) |
| D27 | Viewer facts live in their own `viewer` document kind (at most one per set): each fact is a `select` (2 to 8 values) or a `boolean`, with a required `default`. `specVersion` 5 | Settled | Facts in every view would repeat and drift, and a closed list of values is what lets the state grid list every case. Free-form or numeric facts were left out; they would need bucketing. The default is what a viewer the host says nothing about gets, so authors pick the least-privileged one (RFC 0006) |
| D28 | The viewer input is an array, `[{ fact, value }]`, resolved by `resolveViewer` into a `ResolvedViewer`; a bad or unknown value falls back to the fact's default and is reported in `issues` | Settled | A map keyed by fact id is an index signature (AGENTS.md rule 5). A value that does not fit never reaches a condition, so a typo in the host cannot grant more than the default |
| D29 | Hide, don't disable: a column, field, tab, widget, row action or edit the viewer may not use is not rendered; a hidden dashboard widget leaves its cell empty and the grid is not reflowed | Settled | A disabled control needs a reason and a component prop to say why, and components are not told about the viewer (no registry change). Disabled-with-reason affordances are a possible later slice |
| D30 | `viewerIn` is allowed only in the places `describeContract().conditionPlaces` lists, and is rejected in every `filter` (including count, stat and series widgets) | Settled | A filter becomes a server query and cannot depend on who is asking in the client; letting it would imply a guarantee the server does not give. Viewer-only places take a `ViewerCondition` (`viewerIn`, `and`, `or`, `not`), so a record leaf there is an error |
| D31 | `editableWhen` is a separate key that can only tighten `editable: true`; it needs `editable: true` and never turns editing on. `clearWhenHidden: true` is rejected while a form item's `visibleWhen` reads the viewer | Settled | One flag meaning both "may edit" and "may edit now" would let a viewer rule widen what the document allows. Clearing a field because of who is looking would destroy data when the viewer changes |
| D32 | Per-record `can: { update?, delete? }` is optional, a restriction only (a missing `can` or key means offered, `true` enables nothing), a read-time snapshot for this viewer that the client never sends back. The server still decides and answers a refused write with 403; the client reverts and reloads, which refreshes `can`. The memory and key-value adapters take `recordPermissions` to state and enforce it | Settled | Document conditions know the viewer's facts, not the record: which record is locked is data. A restriction-only flag makes servers that do not implement it unchanged. A malformed `can` is treated as absent. See `docs/records-protocol.md` |
| D33 | The grid gets one axis per viewer fact a view actually reads (a select fact takes the values conditions name plus one "everyone else" value), a `permission` axis on views with an edit surface, and one extra `viewer-not-provided` state; impossible states are pruned | Settled | Facts nothing reads cannot change the page, so they would only multiply states. The not-provided state renders without the `viewer` prop and must look like the all-defaults viewer. A locked record with no records, or a dashboard tab the viewer cannot see, cannot happen |
| D34 | A board's grouping is renderer state, not the document: `groupBy` lists the fields the viewer may choose from (1 to 5, the first is the default), the renderer is uncontrolled unless the host passes `groupBy` and `onGroupByChange`. Cards load once and are grouped on the client | Settled | Which column set a person looks at is a view preference, not a property of the app. One fetch means switching never waits (RFC 0005). A move is optimistic and appended last in its column; any failure reverts, shows the adapter's message and reloads |
| D35 | `layout.Calendar` and `layout.Board` are optional registry keys; without one, that view kind renders an `ErrorSummary` naming the missing key | Settled | Adding a required key would break every existing component set the moment the engine shipped. Each becomes required when the reference set ships it |
| D36 | Record actions are declared on the entity (`actions`: `id`, `label`, optional `confirm`, typed `input`, optional `visibleWhen`; 12 max) and offered by views through `recordActions` on tables, calendars and boards (6 max, in row order; a dashboard embed inherits them). Forms offer actions in slice 2 | Settled | RFC 0007. A command a record runs, not a value it holds, so neither the field list nor the layout. Caps and shapes print from `pnpm describe-registry`; ARCHITECTURE.md §6 |
| D37 | Offering an action hides, never disables: it is offered only while `visibleWhen` (record and viewer leaves) holds and `can.actions[id]` is not `false`; no `enabledWhen`. `availableActions` (`runtime`) is the single source of truth, called by both the renderer and the editor | Settled | RFC 0007 item 2, extending D29. A disabled button needs a reason, and components are not told about the viewer. One formula keeps the editor preview from drifting from the table. Checks `action-offered` / `action-missing` |
| D38 | The action endpoint is `POST {base}/{entity}/{id}/actions/{action}` with `input`, `entityRevision` and a required `baseVersion`, checked before `input`; `200 Record` or `204`; `403` and `409` as for writes; a `datetime` input travels in the one canonical form. No `context` parameter: guarding an action on other state is done by making `version` cover it | Settled | RFC 0007 item 3. Refusal order unknown action → unknown record → `baseVersion` → `can.actions` (34f). See `docs/records-protocol.md` |
| D39 | `DataAdapter.act` is optional and stays optional (owner); a view with `recordActions` on an adapter without it shows an `ErrorSummary` instead of buttons that would fail. The memory and key-value adapters take an `actions` handler map; the HTTP adapter always exposes `act` (an unknown action is the server's `404`) | Settled | RFC 0007 item 4; owner answer 1: allow, don't forbid — existing adapters unchanged (34f, 34g) |
| D40 | `layout.Dialog` is the RFC's only new registry key (shared with RFC 0003 slice 2) and stays optional like D35's Calendar and Board: the renderer builds the dialog content, the component supplies only modal behaviour. An action with `input` always confirms, one with only `confirm` confirms, a bare one runs on press | Settled | RFC 0007 item 5; owner answers 1 and 4 — a document asks for a confirmation when it wants one (35a) |
| D41 | `datetime` stores one canonical form — UTC, milliseconds, `Z` (`toISOString`) — so string order is time order for every adapter, the in-memory sort and a SQL `ORDER BY`; it displays in the viewer's zone (the Display gets the formatted `text` beside the stored value), ranges filter by minute from the viewer's clock, conditions have no `contains`, and it is not a calendar `dateField`, a board `groupBy`, or relative-valued in slice 1. `fields.datetime` is optional; a registry without it shows an `ErrorSummary` | Settled | RFC 0007 item 6; owner answer 3 (milliseconds UTC is fine). One form means nothing parses to compare (35b added the Display's `text` extra). See `docs/records-protocol.md`, "Datetimes on the wire" |
| D42 | `compare` on a text column: `{ "to": "previousRow" \| "nextRow" }` or `{ "field": <other text field> }` of the same record; the column's value is the after, the comparator the before; the word diff is computed in `runtime` and drawn through an optional `diff` prop on the text `Display`; never together with `editable` | Settled | RFC 0007 item 7 — a version history shows what changed without the server keeping diffs. A cursor page cannot widen backwards, so the previous page's last row goes as an explicit `edge` (34d); checks `diff-missing` / `diff-offered` (35j) |
| D43 | `Page.total` is optional and `next` is an opaque cursor the client passes back untouched; the table keeps Previous/Next with a client-side cursor stack and no "load more"; the mode is response-driven (`total` → offset, `next` without `total` → cursor, neither → last page); counts walk pages to the 5,000 cap and report "5000+" | Settled | RFC 0007 item 8. Appending rows grows the DOM without bound and moves focus (34h, 35e). See `docs/records-protocol.md`, "Paging without a total" |
| D44 | Read-only needs no new key: a table without editable columns or offered actions is read-only. Nested data is join entities plus drill-down (`rowAction` chains); evidence is pre-joined text in slice 1. A dashboard drill target stays slice 2 unless pre-joined text proves too limited | Settled | RFC 0007 item 9; owner answer 2 still open. New keys duplicating what exists rot |
| D45 | `specVersion` 5 → 6 with an identity `migrate()` step: the version adds `datetime`, entity `actions`, view `recordActions`, column `compare` and optional page totals (RFC 0007); every version-5 document stays valid | Settled | RFC 0007 item 10; AGENTS.md rule 8. `SPEC_VERSION` is 6 in `core` |
| D46 | The state checks read the props passed to the registry, never the DOM, and take their expectations from the same runtime formulas the renderer uses (`availableActions`, `compareCells`) | Settled | 35k/35j (`d0853c2`). A kit that reads the DOM would dictate one component set's markup; its own expectations could drift and both be wrong. Extends D23 |
| D47 | `StatesPreview` names the action and paging axes on a second line ("States this view varies"), separate from the viewer-fact line: the viewer axes answer what the viewer is told, the product axes what the product varies | Settled | 37e. An author editing a view needs to see what the grid varies without reading axis ids |
| D48 | `series` ships as its own widget (not `stat` with an optional `groupBy`), `specVersion` 6 → 7 with an identity `migrate()` step: one `groupBy` field (select, boolean, reference, text or date — a number is refused), `bucket: "day" \| "week" \| "month"` only on a date (week keys the ISO Monday, month keys `YYYY-MM`), the slice-1 `Measure` unchanged, `display: "table" \| "bar" \| "line"`, `sort` default `{ by: "group", dir: "asc" }`, `limit` default 50 max 200; empty group values are skipped and counted; a date series sorted by group gap-fills (0 or no value) and `limit` keeps the newest buckets; the same 5,000-record ceiling and `partial` as `stat`; drawing is the components repo's job behind the optional `widgets.series` key | Settled | RFC 0001 slice 2 (decisions, 2026-10-21) — see that section for all eight calls. | D52 | AGENTS.md rule 8 changes: `specVersion` bumps only for a change that needs a migration (a rename, a removal, a changed meaning, a new required key), with a real `migrate()` step and a before/after fixture pair. A purely additive change (a new optional key, value or field type) does not bump; it lands with valid and invalid fixtures, a `describeContract` entry and a changeset naming the core version that introduced it. | D53 | After a record action, a done toggle or a move the viewer made, focus returns to the **same record** by id, never by place: to the same kind of control it pressed, else to the trigger of the panel that held it (`data-yadad-focus-return`), else to the record's first focusable control. An update that answers with a new id is followed by that id. Records are found inside their own view only (`data-yadad-record`, `data-yadad-record-view`). The return stays armed until the action's newer data has landed (capped at 60 s) and gives up at once if the viewer presses a key, presses a pointer or moves focus elsewhere. A record that left the view leaves focus alone | Settled | Place-based returns sent focus to a neighbour after a re-sort or move, and a fixed 1.5 s window lost focus behind a slow HTTP reload. Each fix proven only in the showcase failed in a real host, so focus changes are checked against a real HTTP host as well (renderer 0.18.0 to 0.18.7, 2026-10-28) |
